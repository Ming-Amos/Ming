# Ming 产品与开发计划

版本：v0.3 · 2026-09-25  
依据：同目录 `MING_PRD.md` v0.6 及 `MING_SUBMISSION_CHECKLIST.md`。本版取代旧版 Bob 优先运行、无需模型 API 的方案。本文为规划，不是已实现功能清单。

## 1. 我们要解决的唯一核心问题

> 在借助 AI 开发项目的过程中，AI 告诉我功能完成了，但我还得自己打开页面、逐项点击、截图报错，再解释给 AI 听。每次修改后，还要重新检查一遍。

**Ming 接手重复的验收操作与问题反馈。**用户告诉 AI 想要什么，Ming 帮助检查实际行为是否符合要求，把失败证据返回 AI，并在修复后再次检查。

第一批用户：使用 Bob 开发本地网页应用的独立开发者和小团队。项目可以从零开始，也可以已有代码。业务内容可以不同；日报是样例，不是产品类别。

产品最小价值：用户完成一次范围确认后，不再为了同一条已登记的功能反复点击页面、手工截图、复制报错和重新描述复现步骤。

## 2. 用户真正如何使用

### 第一次接入

1. 用户在 Ming 网页创建项目，填写可访问的测试地址、功能说明或 PRD。首先支持无复杂登录的受控网页；配置按项目保留。
2. Ming 后端调用用户自备的模型 API，读取需求及页面结构生成草案。现有页面只用于理解操作方式，正确性由需求决定；不默认把整个项目源码发给模型。
3. Ming 展示一份自然语言清单，例如“修改任务名称后，刷新仍保留新名称”。用户核对或调整；无需读测试代码。
4. 模型输出经过校验的结构化执行计划；已确认的标准和计划由 Ming 执行。定位失败、工具异常等应单独标明；不得执行模型返回的任意程序。

### AI 完成开发后

1. 用户在 Ming 点击“开始验收”；接好 Bob 工具并约定流程后，也可由 Bob 完成开发时主动调用，后者须验证后开放。
2. Ming 在浏览器中执行操作与检查，记录真实结果。
3. 有失败时，网页整理修复任务；Bob 在已连接且获指令处理任务时，通过 MCP 读取证据，用户无需逐项截图和重新描述。网页不能凭 MCP 反向唤醒 Bob。
4. Bob 在已授权的项目工作范围内修复，再次调用 Ming。
5. 用户查看通过项、仍失败项和未验证内容；后续修改继续复用这些检查。

每轮不增加重复的标准确认。需求和标准发生实质变化时才需要重新核对；Bob 本身的工具权限仍按用户配置执行。

## 3. Ming、Bob 与用户的职责

| 参与者 | 负责的工作 | 完成后留下什么 |
| --- | --- | --- |
| 用户 | 提供业务预期，核对验收范围，决定有歧义的规则 | 需求与确认后的标准 |
| Bob | 开发 Ming；运行时读取证据、理解目标代码、修复并复验 | 实际会话、代码变更、修复记录 |
| Ming 后端模型 | 从需求与页面信息提出标准草案、受限操作计划和原因假设 | 带来源的结构化输出及用量 |
| Ming 服务与执行器 | 管理确认、执行操作和断言、整理证据、返回结果、对比复验 | 可追溯的验收记录 |

用户已选择自费国内模型 API，尚未完成模型定型和密钥配置。先做一个服务端供应商适配器，配置模型 ID、地址和本机密钥；先验证一个供应商，不开发模型市场。Bobcoins 与这个 API 的费用分别记录。阶段 A 不需要密钥；阶段 B 需真实连接后才能通过验收。

## 4. 第一版必须做的六项能力

| 优先级 | 能力 | 用户得到的结果 | 通过条件 |
| --- | --- | --- | --- |
| P0 | 接入项目和需求 | 项目对应的自然语言验收清单 | 不含写死的业务名称、路径和字段 |
| P0 | 执行实际验收 | 明确知道哪些功能通过 | 断言实际执行，不能只生成报告文字 |
| P0 | 自动收集失败证据 | 不需要手工截图和整理错误 | 每个失败关联具体步骤、预期/实际结果和证据 |
| P0 | Bob 读取结果并修复 | 减少重新解释问题 | Bob 能通过工具取得足够的复现信息 |
| P0 | 重复验收和前后对比 | 修完能再次检查，也复查旧项 | 相同标准可重复执行，历史结果不覆盖 |
| P0 | 跨业务项目复用 | 同一工具可以用于另一项目 | 第二个项目只更换测试与配置，不改 Ming 核心 |

P1 在 P0 全部完成后考虑：完整操作回放、更多浏览器、自动检测代码变化、结果导出美化。

不投入本轮：全栈应用生成器、自动部署、移动端、小程序、支付/验证码等外部流程、智能测试筛选、账户付费平台。涉及视觉美感等主观要求时保留人工判断，不伪装为自动验收已覆盖。

## 5. 功能依据与验收生成

优先级：用户明确要求 → 已确认的 PRD/功能说明 → 用户确认后的推断。

每条条件包含：来源、编号、前置条件、用户操作、预期结果、测试数据与证据要求。模糊需求先指出歧义，例如“提交成功”是否还要求刷新后保留。

用户确认业务标准后，可以调整页面定位和执行细节，但必须记录计划变化。若预期结果、断言强度或覆盖范围降低，需要显示为标准变化，不能当成同等条件下修复成功。模型输出 schema 校验失败或必要信息不足时返回可读问题，不静默回退到演示答案。

首次建立测试确实有成本。必须同时记录接入成本与后续节省的人工工作，不把首次生成步骤从效果计算中隐去。

## 6. 三个主要视图

视觉基准已选择“应用透视图”，见 `MING_VISUAL_DIRECTION.md` 和 `assets/ming-application-xray-concept-v1.png`。下列三个视图是任务、运行和对比状态，不要求制作三个割裂的页面；可在同一画布中切换和展开。

### 验收任务

- 顶部：项目、测试地址、本次需求。
- 主区：自然语言验收条件及来源；标记待确认、可执行和需补充信息。
- 操作：确认范围、开始验收。已确认范围重跑时不重复确认。

### 运行结果

- 顶部：本轮范围、通过/失败/阻塞/未执行数量。
- 主区：需求对应的检查结果。
- 展开失败：复现步骤、预期与实际、截图、必要的请求或浏览器错误。
- 操作：查看证据、重新验收、加入修复任务。连接后 Bob 可通过工具读取；未连接时明确提示，不能假装已通知。
- 修复状态必须有依据：只有 Bob 实际开始处理才显示处理中，等待时明确显示等待。

### 修复对比

- 对应两次运行、应用版本、标准版本和测试实现版本。
- 展示仍失败、新通过、新失败、未执行项目。
- 原始失败证据仍可打开；标准不同的比较明确标注“验收条件已变化”。

## 7. 建议技术结构

主流程：**Ming 网页 → 本地服务 → 模型 API 生成草案 → 用户确认 → Playwright 实际执行 → 网页结果与证据。**

修复流程：**网页建立修复任务 → Bob 主动调用 Ming MCP 读取证据 → Bob 修改目标应用 → Bob 或网页发起复验。**

- 本地服务：TypeScript/Node.js；对网页提供接口，维护项目、标准、任务、运行状态和结果，开发期间绑定本机地址。
- 模型层：服务端调用用户配置的供应商；保存调用用量、错误类型与经过校验的计划。密钥不进入网页包、日志或公开仓库。
- 执行层：Playwright，先支持 Chromium；统一解释受限 JSON 步骤和断言。API 或 Test runner 的封装由 Bob 在阶段 A 选择，不能形成两套结果来源。
- 网页层：React/Vite；先完成输入、确认、运行和证据，再实现应用透视图。
- 存储：按项目、任务、运行分别保存 JSON 和证据文件；第一版不引入数据库服务。
- Bob 连接：本地 MCP 适配器调用同一个验收服务，避免网页端和工具端产生两套状态。
- 长任务：开始执行即返回运行编号，通过结果查询获取进度，避免把整场验收压进一次同步工具响应。
- 项目需求、定位与执行计划属于项目数据，不把日报业务写进通用引擎。阶段 A 的固定计划标记为开发夹具，阶段 B 替换为真实模型生成的草案。

建议服务契约：保存项目、生成草案、确认计划、开始验收、读取结果、获取证据、比较运行。阶段 C 的 MCP 复用这些契约，另提供读取/认领修复任务。开始执行不得隐式把草案标记为已确认。

这一选型适配网页业务，不表示任何框架、复杂登录或第三方依赖都已适配。目标项目必须先能运行；启动障碍作为阻塞反馈，不扩展为通用环境修复平台。

提交页面要求演示平台与应用 URL。目标是提供受控样例的在线实际验收，最迟阶段 B 结束前验证承载方式；只提供历史回放是否符合要求尚待确认，不能默认豁免。静态网页托管不等于已经具备浏览器执行后端。远程服务器不能通过 localhost 访问参赛者电脑上的目标项目；首版在线演示使用服务器可访问的隔离样例，本地项目使用本地 Ming。需要付费时先列明实际方案和费用，再由用户决定。

## 8. 执行结果必须可信

- 业务结果：通过、断言失败、前置条件阻塞、未执行。
- 执行异常：页面定位失败、工具错误、超时等单独说明，不直接断言为业务缺陷。
- 无法稳定复现的结果显示不稳定；不隐藏第一次失败或只展示重试成功。
- 每次独立浏览器上下文和测试数据；相互依赖的步骤在同一场景中按序运行，其他场景不依赖执行顺序。
- 重跑当前范围内全部已登记检查；“全部”仅指已登记范围，不等于验证了整个软件。
- 用已知正常和已知有缺陷的版本验证断言，排除永远通过、只检查成功提示而忽略真实结果的测试。
- 记录未提交代码的相关文件指纹，仅记录 Git 提交号不足以区分修复前后版本。
- 默认在指定测试项目和本地环境运行；证据输出隐藏凭证，不上传完整敏感配置。
- 工具报错或连续两轮修复无进展时停止自动重试，保留证据与未解决项，避免消耗用量却没有进展。

## 9. 两个验证项目

### 项目 A：简化日报网页

三个条件：非空提交显示、刷新后保存、空内容校验。预置缺陷：提交后只更新页面状态，刷新丢失。必须明确标注为预置示例。

### 项目 B：独立待办列表网页

三个条件：新增任务显示、切换完成状态、刷新后完成状态保留。以状态切换为差异点，项目路径、页面结构和字段与 A 分开。

验收第二个项目时，不修改 Ming 核心，仅新增项目配置、条件和测试。若必须修改核心，记录原因并修复抽象，再从头验证两者。

这两个样例只能证明跨这两类业务复用。更多项目适配通过后再扩大产品声明。

## 10. 给 Bob 的阶段任务

每阶段先阅读 PRD 与本计划，只执行当前阶段。完成后提供：改动、实际检查结果、未完成项、下一阶段依赖；不要将计划中的能力描述为已实现。

每次与项目相关的 Bob 会话结束后及时保存摘要截图，并记录成员、任务、对应代码/文件与验证结果。会话 Markdown 导出作为建议补充；截图是本届已明确的必交项。按开赛后指南核对具体截图方法。

| 阶段 | 工作 | 必须展示的证据 |
| --- | --- | --- |
| A：网页真实执行 | 最小网页、服务、通用执行器和隔离日报样例；固定开发夹具含三条标准 | 网页触发真实运行；刷新丢失版本正确失败，正常版本正确通过；截图和历史记录可读 |
| B：需求到执行 | 接通真实模型 API，需求与页面信息生成草案和受限计划，用户确认后运行 | 输入变更产生对应草案，来源可追溯；密钥未配置和生成失败如实显示；记录用量 |
| C：失败到复验 | MCP 读取/认领修复任务和证据，Bob 据此修改样例并复验 | 同版标准先失败后通过；不是切换预置正常模式冒充 Bob 修复；用户没有手工整理复现材料 |
| D：跨项目与界面 | 接入第二个项目，完成三个视图 | 不改核心执行第二套业务，报告能打开原始证据 |
| E：评估与交付 | 记录对比、录屏、公开仓库与应用访问检查、两份说明、封面和幻灯片 | 按提交清单逐项验收；视频≤180秒且实际运行≥90秒，两份说明各≤500 words，成员 Bob 摘要截图齐全 |

A 失败时先排查服务、页面定位及执行方式。A 成功只证明执行器与网页链路，不代表模型理解或 Bob 修复已完成。阶段 A 详细任务在产品工作目录的 `BOB_START_HERE.md` 中。

建议 48 小时预算：A 4 小时，B 7 小时，C 8 小时，D 7 小时，E 6 小时，休息与故障缓冲 16 小时。这是安排上限，不是开发耗时保证；核心代码按比赛窗口和主办方说明开展。

缩减顺序：先删动效和自制回放，再删额外浏览器和报告导出；保留真实执行、错误证据、Bob 读取、重复验收、第二项目验证。来不及时明确未完成能力，不用伪造结果补齐演示。

## 11. 如何证明节省了工作

对比同一任务的独立副本：

- A：Bob 开发，用户手工验收并向 Bob 反馈。
- B：Bob 开发，Ming 执行验收并把证据返回 Bob。
- 如有余力，加测 Bob 直接使用已有测试工具，确认 Ming 的标准追溯与重复验收是否有额外价值。

每次记录初始版本、功能范围、标准、执行顺序及参与人。交换顺序或重复案例，说明熟悉任务的影响。

| 指标 | A 人工验收 | B Ming 验收 |
| --- | --- | --- |
| 首次准备/接入时间 | 待测 | 待测 |
| 单轮验收总时间 | 待测 | 待测 |
| 人工实际操作时间 | 待测 | 待测 |
| 点击、截图、复制、解释次数 | 待测 | 待测 |
| 实际缺陷检出数及漏报/误报 | 待测 | 待测 |
| 修复后复验时间 | 待测 | 待测 |
| Bob 用量（可获得时） | 待测 | 待测 |
| Ming 模型调用数、token、费用 | 不适用或如实记录 | 待测 |

不得只用“测试通过率”证明产品价值；也不能省略工具失败、测试维护和首次配置成本。小样本以案例结果呈现，不外推总体提速。

## 12. 演示视频提纲

依据 2026-09-25 用户提供的本届要求：MP4，最多 180 秒，至少 90 秒在屏幕上展示解决方案实际运行；包含讲解，并清楚展示 IBM Bob 如何被使用。目标成片 175 秒，留 5 秒余量：

| 时间段 | 内容 | 素材安排 |
| --- | --- | --- |
| 0:00–0:15 | 痛点与 Ming 的用途 | 简短开场 |
| 0:15–0:35 | 读取需求、确认验收项 | 真实操作录屏，20 秒 |
| 0:35–1:15 | 自动检查、发现缺陷、查看应用透视图与证据 | 真实操作录屏，40 秒 |
| 1:15–2:05 | Bob 读取证据、修复、Ming 使用相同标准复验 | 真实操作录屏，50 秒；长等待可剪辑，标明时间跳转 |
| 2:05–2:25 | 第二个项目的验收过程 | 真实操作录屏，20 秒 |
| 2:25–2:45 | 实测效果与支持范围 | 数据及限制说明，不使用未测数字 |
| 2:45–2:55 | 项目名称与访问方式 | 简短结束 |

计划保留 130 秒真实使用录屏。最终按剪辑成片重新核对，确保至少 90 秒确实展示方案运行；概念图、幻灯片、片头、静态介绍和等待画面不用于凑实际运行时长。配讲解，不能只播放无说明的页面。

核心叙事：“过去每次都要我重新检查；现在标准留下来，操作可重复，失败有证据，AI 可以接着修。”
