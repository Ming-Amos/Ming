## Fix before declaring Stage A complete

1. **Preserve the dependent scenario's browser state.** `packages/runner/src/plan-runner.ts:238-243,282-283` creates and closes a browser context for every criterion. The fixture's AC-02 begins with `reload`, so it currently refreshes a new blank page rather than AC-01's submitted report. Share the same page/context for AC-01 and AC-02; keep AC-03 isolated. Express this through generic scenario/dependency data rather than hardcoding criterion IDs in the runner. Verify normal = three passes; buggy = AC-01/03 pass, AC-02 fails; failed AC-01 blocks AC-02 without executing it.

2. **Hash the complete execution plan consistently.** `packages/runner/src/fingerprint.ts:4` uses top-level keys as a JSON.stringify replacer whitelist, stripping nested fields. In `apps/server/src/index.ts:74`, hashing the criteria array serializes it as `[{},{},{}]`; step changes therefore do not change that fingerprint. The runner also hashes a different object at `plan-runner.ts:310`. Use one canonical serialization/hash definition preserving nested criteria, steps, assertions and dependencies, excluding the computed fingerprint itself. Verify changing a nested expected value or locator changes the hash; normal and buggy runs of the unchanged plan have the same hash; the displayed/confirmed hash matches the saved run hash.

3. **Complete and strengthen the actual fixture assertions.** `fixtures/stage-a-plan.json:79-104` tests only the empty string, despite AC-03 promising whitespace coverage. Add a separate pure-whitespace submission and check both validation feedback and unchanged record count. Also scope AC-01/02 content assertions to the record list: `plan-runner.ts:143-148` currently searches all page text, so echoed input or a success message could satisfy the check without a saved list entry. Keep the scope/locator in plan data. Verify both invalid-input cases actually execute and a missing record cannot pass merely because its text appears elsewhere.

4. **Reject structurally invalid plans before browser execution.** `plan-runner.ts:35-54` accepts empty criteria/steps, missing step-specific fields and invalid dependency references. Empty or wholly blocked plans can then be reported as passed by `:355-363`. Validate the required field types for each registered step, nonempty executable coverage, unique IDs and valid dependency ordering/references. Do not accept an invalid count expectation or missing locator as a business failure. Verify malformed plans are rejected explicitly and cannot produce a green result with no executed assertions.

5. **Bind confirmation to the plan actually shown.** `apps/server/src/index.ts:114-119` checks truthiness, so strings such as `"false"` are accepted; `:137` reloads the plan without checking the user's confirmed version. Require a real boolean confirmation and the current plan ID/version/fingerprint (or equivalent server confirmation record). Reject stale confirmation after a plan change. Verify unconfirmed, nonboolean and stale-confirmation requests do not start a browser; an unchanged confirmed plan can be rerun without repeatedly asking the user.

6. **Close failed jobs reliably and retain unexecuted criteria.** Plan validation throws before the runner's try/catch (`plan-runner.ts:307`), while the server job has no rejection cleanup (`apps/server/src/index.ts:139-150`). A rejected job can remain in runningJobs, leave no result, or become an unhandled rejection. Handle rejection and cleanup in a guaranteed path: reject invalid input before returning a run ID, or save a terminal error for every returned run ID. On browser launch/context failure, preserve all planned criteria and mark unexecuted work explicitly; currently `criteriaResults` can be empty and contracts have no `not_run` status (`packages/contracts/src/index.ts:53-55`). Verify missing browser/target and malformed-plan cases terminate truthfully, leave no hanging progress, and distinguish error, blocked and not_run.

7. **Report actual progress rather than a fixed count.** `apps/server/src/index.ts:161-168` always returns `finishedCriteria: 0, totalCriteria: 3` while running. Feed real criterion/step updates from the runner into the saved or in-memory run state and derive totals from the plan. Verify polling reflects completed criteria before the whole run ends and final state remains available in history.
