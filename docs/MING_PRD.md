# Ming 精简 PRD

版本：v0.6 · 2026-09-25  
状态：开赛实施基线；核心功能尚未开发。已按用户最新决定改为网页入口、独立模型 API、Bob 开发和修复。技术方案需通过实际运行验证。

## 1. 产品定位

**Ming — Every “done” comes with proof.**  
**每一句“已完成”，都有据可验。**

Ming 帮助使用 AI 开发网页应用的独立开发者和小团队，把功能需求变成可执行的验收条件，运行检查、保存失败证据，并将结果交给 Bob 修复后再次验证。

核心目标：减少开发者手工点击验收、整理错误信息、反复解释问题和重复验证的工作。

用户明确的核心痛点（后续产品取舍均以此为准）：

> 在借助 AI 开发项目的过程中，AI 告诉我功能完成了，但我还得自己打开页面、逐项点击、截图报错，再解释给 AI 听。每次修改后，还要重新检查一遍。

产品承诺：根据功能需求执行验收，收集失败证据并反馈给 AI，在修复后重复验证，减少人工检查和沟通成本。用户负责明确预期和决定功能取舍；不要求用户自己编写测试代码或手工整理每一次错误。

**Ming 面向不同业务项目，日报仅是演示样例。**验收条件、页面操作和预期结果应根据接入项目及其功能需求生成，不能将日报字段、页面地址或三条示例检查写死在产品逻辑中。产品长期目标是扩展到更多项目类型；比赛版首先支持能够在本地测试环境中运行、可通过浏览器操作的网页应用，不承诺任意项目零配置接入。

已有代码和页面可帮助识别现有功能，却不能单独证明用户原本想要什么。验收依据应优先来自用户需求、PRD 或功能说明；缺失时先形成待确认草案，不能把当前错误行为直接当成正确标准。

适用场景：

- 从零创建项目：验收第一个可用功能。
- 接手已有项目：验收新增或修改的功能，复查相关已有功能。

两个场景使用同一套验收流程。第一版不另做项目生成器。

## 2. 用户问题与预期改善

| 当前问题 | Ming 的处理 | 可观察的改善 |
| --- | --- | --- |
| 一句自然语言需求没有明确完成标准 | 在开发或验收前，形成可检查的条件，由用户确认 | 减少完成标准不一致造成的返工 |
| AI 修改代码后，用户仍需逐项操作页面 | 执行已经确认的验收任务 | 减少重复人工操作 |
| 失败后需要截图、复制报错、重新描述 | 收集操作步骤、截图及相关错误，关联到失败条件 | 缩短整理问题的时间 |
| 修复后不知道同一个问题是否真的解决 | 在相同条件下重跑验收，保留前后结果 | 更容易核对修复效果 |
| 全绿报告可能遗漏未测试内容 | 明确显示通过、失败、阻塞、未执行和过期结果 | 用户能理解验证范围 |

## 3. 第一版完整流程

1. 用户在 Ming 网页中创建项目，填写测试环境地址，导入本次功能的 PRD 或需求说明。第一次保存后可重复使用，不需要每轮重新上传项目或 PRD。
2. Ming 后端调用用户配置的模型 API，根据需求及页面结构生成验收草案与受限的执行步骤。用户核对标准，歧义标为待确认；模型不能替用户编造业务规则。
3. Bob 或其他开发工具完成修改后，用户在 Ming 网页发起验收；Ming 对已经运行的测试应用执行真实浏览器操作和断言。
4. Ming 生成结果：条件、实际步骤、预期结果、实际结果及证据。
5. 用户将失败加入修复任务；在 Bob 已接入 Ming 工具并被要求处理任务的工作流程中，Bob 主动读取证据并修改目标项目。
6. 修改完成后，Bob 再次调用 Ming，复用同一版验收条件并复查相关已有检查，展示前后对比。第一版可由 Bob 或用户发起重跑；持续监控文件变化并自动触发属于后续扩展。

产品以网页为主要入口。模型负责理解需求与辅助分析；Playwright 执行器负责实际操作和明确断言；Bob 负责开发 Ming，并在连接后读取证据、修复目标项目。MCP 的调用方向是 Bob → Ming，不能假设网页可以反向唤醒或命令 Bob。等待 Bob 读取时如实显示等待状态；自动触发能力须实际验证后才能宣传。

## 4. 比赛演示场景

使用不包含真实用户数据的简化日报网页作为测试对象。日报网页是演示样例，Ming 才是参赛产品。

为了验证通用性，另选一个独立的待办列表网页作为迁移样例，验收新增任务、切换完成状态及刷新后状态保留。两种项目共用 Ming 的执行和证据能力，只新增各自的验收说明、测试步骤及接入配置，不为第二个项目修改 Ming 核心逻辑。

需求：员工可以填写、提交和查看自己的日报。

| 编号 | 验收条件 | 执行动作 | 通过依据 |
| --- | --- | --- | --- |
| AC-01 | 非空日报可以提交并显示 | 输入唯一测试内容并提交 | 页面出现与本次内容一致的日报记录 |
| AC-02 | 刷新后日报仍存在 | 在 AC-01 成功后刷新页面 | 同一条记录仍然可见 |
| AC-03 | 空内容不能提交 | 空输入时尝试提交 | 显示校验提示或禁止提交，且未新增空记录 |

如 AC-01 失败，依赖它的 AC-02 应显示“阻塞”，不能误报为通过。每次测试使用独立测试数据，避免旧记录导致误判。

演示可使用明确标注的预置缺陷，例如刷新后数据消失。展示实际执行、失败证据、Bob 修复及再次运行，不把预置案例描述成未知线上故障。

## 5. 第一版功能范围

### 必须完成

- **验收任务**：保存原始需求、条件编号、前置条件、操作步骤、预期结果和标准版本。
- **条件确认**：用户能查看并确认验收范围；标准变更生成新版本，报告明确显示变化。
- **项目接入**：网页中按项目保存测试环境、需求、已确认标准和执行步骤；业务名称、字段及页面定位信息均来自该项目配置或生成的计划。
- **模型接入**：Ming 后端使用用户自备的国内模型 API。供应商和模型可配置，先验证一个供应商；具体模型尚未最终确认。密钥仅保存在本机服务端配置中。
- **实际执行**：第一版优先支持本地网页应用中的点击、输入、页面跳转、内容断言及刷新后状态检查，组合成不同业务功能的验收。固定测试环境用于控制比赛范围，不将目标应用限制为日报业务。
- **证据报告**：每项结果关联执行记录、必要截图及相关浏览器或请求错误；区分观察事实和模型/Bob 的原因推测。
- **修复交接**：Bob 能读取指定运行的失败证据，针对应用代码修复后重新验收。
- **前后对比**：展示同一版条件的两次运行结果，并能打开原始证据。
- **重复验收**：同一项目中已确认的验收项持续保留；第一版在每次功能修改后重跑当前范围内全部已登记检查，避免未验证的“智能筛选”漏掉旧功能。功能需求发生变化时再更新相应标准。

### 暂不纳入

- 任意需求的一键建站、任意技术栈和任意网站适配。
- 自动部署、完整项目管理、团队账号和收费系统。
- 微信小程序、手机原生应用、生产环境操作。
- 全站安全审计、压力测试、完整代码质量评分。
- 验收全绿即宣称软件没有缺陷或已经达到生产要求。

这里不做的是产品内的自动部署功能。比赛交付仍需准备 Demo Application Platform 与 Application URL，不能因采用本地工具架构而遗漏；具体访问方案见提交清单。

## 6. 产品形态与页面

建议形态：**网页验收工作台 + 本地执行服务 + 模型 API + Bob 工具连接**。先本地端到端跑通，再安排评委可访问的受控在线演示。

已选视觉方向：**应用透视图**。用户选择的是第二轮概念图中的第一张：以实际页面为中心，周围展开需求、操作记录、请求证据、失败结果和 AI 修复任务。采用浅色画布与清晰关系连线，不采用此前的光路、放映室、试验场或功能地形地图。

视觉基准存放于 `assets/ming-application-xray-concept-v1.png`，具体设计要求见同目录 `MING_VISUAL_DIRECTION.md`。选定的是整体形式；概念图里的示例数据、文案和状态必须在实现时替换为真实结果。

第一版只需三个主要视图：

1. **验收任务**：需求、条件列表、目标应用地址、确认状态。
2. **运行详情**：正在执行的步骤、通过/失败/阻塞/未执行状态、截图和错误证据。
3. **修复对比**：修复前后结果、对应代码版本或文件指纹、验收标准版本及未覆盖范围。

界面突出“哪条需求没达到，证据是什么”，不以聊天记录、装饰性评分或无依据的完成百分比作为主要内容。

## 7. Bob 的作用与技术验证

Bob 参与两个层面：

- **开发 Ming**：规划、编码、测试、调试，保存真实会话与提交记录。
- **使用 Ming**：通过工具读取已确认标准、执行结果与证据，修复目标代码并发起复验。用户不必把截图和错误逐项复制给 Bob。

建议技术组合：Node.js/TypeScript 本地服务、React/Vite 网页、Playwright 浏览器执行器、模型供应商适配层、MCP 接口。依赖版本由 Bob 在实施时核实兼容性并锁定。

Ming 后端模型负责将 PRD 转成带来源的标准草案，以及根据页面信息生成结构化操作计划；计划通过校验和用户确认后，由 Playwright 执行。模型可以提出原因假设，不能仅凭一段分析把检查标为通过。不得将现成测试工具的能力宣称为 Ming 独有创新。详细阶段任务见同目录 `MING_BUILD_PLAN.md`。

用户已选择自备付费国内模型 API；当前未配置密钥，未测量模型效果或成本。阶段 A 使用明确标注的开发夹具验证执行器；阶段 B 必须接通真实模型，不能以固定模板冒充模型生成。

网页与 Bob 工具共用以下服务能力，先验证网页调用，再接 MCP：

| 能力 | 输入 | 输出 |
| --- | --- | --- |
| 执行已确认的验收 | 验收任务编号 | 本次运行编号与状态 |
| 读取运行结果 | 运行编号 | 各项结果、错误证据及证据位置 |
| 比较两次运行 | 两个运行编号 | 前后变化和标准是否一致 |

由 Bob 调用 Ming；不依赖 Ming 获得一个尚未确认存在的 Bob 云端 API。

官方接入参考：[IBM Bob MCP 文档](https://bob.ibm.com/docs/ide/configuration/mcp/mcp-in-bob)。文档支持接入方向，不代表本项目已经完成接入测试。

## 8. 验证可信度要求

- “通过”必须来自实际执行的断言；截图用于帮助理解，不能单独证明所有条件成立。
- 执行器故障、应用不可达、前置条件失败分别说明，不伪装成业务通过。
- 每次运行记录时间、应用版本或相关文件指纹、验收标准版本和测试实现版本。
- 应用或测试发生变化后，旧报告保留为历史结果，并显示需要重新验证。
- 用户确认后的标准不可静默降低；测试实现如有改动，必须在对比中明确显示。
- 验收在测试项目和测试数据上执行；证据展示前隐藏凭证及敏感字段。
- 生成的测试也可能有误：用明确失败和明确成功的样例检查测试是否能正确区分，不能仅因为 Bob 写了测试就相信它。
- 模型计划仅允许经校验的浏览器操作和断言，不执行模型生成的任意脚本或终端命令。不能访问、定位或执行时明确返回阻塞或执行异常。

## 9. 完成标准

比赛版达到以下条件，才算完成：

1. 用户能在网页输入需求，通过真实模型生成并确认标准，发起真实验收；Bob 能通过工具读取证据和发起复验。
2. 三条演示验收条件均有实际执行结果和可查看证据。
3. 有缺陷的版本能够稳定触发相应失败；修复后相同条件通过。
4. 原来通过的相关检查在修复后继续执行，结果如实呈现。
5. 标准变化、执行阻塞和未验证内容不会被隐藏。
6. 至少完成一次从需求到失败、修复、复验的真实录屏。
7. 在日报与待办列表两个独立项目上执行各自的验收，证明业务步骤可替换，Ming 核心逻辑无需随业务更改。只验证这两个项目时，不宣称已经适配所有网页应用。
8. 完成提交材料：两份各不超过 500 words 的说明、公开代码仓库、每位成员的 Bob 任务会话摘要截图、演示平台与应用地址、封面、幻灯片，以及不超过 180 秒且至少 90 秒展示实际运行的 MP4 视频。视频包含讲解并展示 Bob 的具体使用。

## 10. 如何衡量流程改善

比较“直接使用 Bob 加人工验收”与“Bob 配合 Ming”。使用同一初始代码、同一需求和同等测试数据，分别在独立副本中执行。

记录：

- 从代码交付到完成验收的用时。
- 人工点击、复制证据、解释失败和重新发起操作的次数。
- 发现的实际缺陷、误报和漏报。
- 首次接入与编写验收的成本，以及后续重复验收成本。
- Bob 用量（若可获得），作为成本记录而非预设优势。
- Ming 所用模型的实际调用数、token、耗时和可核实费用；模型用量与 Bobcoins 分开记录。

小样本结果只说明本次案例的表现。提前设计记录表，完成实际运行后再填数据，不预先承诺提速百分比。按条件允许交换执行顺序或重复案例，并说明人工熟悉任务造成的影响。

## 11. 比赛期间的实施顺序

1. **真实执行**：网页发起已确认的开发夹具检查，对隔离的日报样例执行三项断言、收集截图。用正常版和预置缺陷版检查执行器是否可靠。
2. **需求理解**：接通用户模型 API，网页输入 PRD，产生可追溯的标准与受限执行计划，经确认后执行。
3. **修复复验**：Bob 通过 MCP 读取真实失败证据，修改目标应用，按同版标准复验。
4. **迁移与界面**：第二个独立项目不改 Ming 核心即可验收；完成应用透视图、历史记录和版本对比。
5. **效果与交付**：准备可访问的应用地址、实测数据、视频、说明及真实 Bob 使用材料。

开发工作目录使用 `C:\Bob\Projects\Ming`，仅放参赛产品、玩具样例及所需文档，不导入真实日报系统和数据库。比赛窗口：北京时间 2026-09-25 23:00 至 2026-09-27 23:00。当前只整理交接材料，核心实现交给 Bob。

## 12. 尚待验证的关键问题

- 本机 Bob 的 MCP 配置及调用是否能稳定工作。
- 从自然语言条件生成可靠浏览器检查的成功率，哪些需要人工调整。
- 用户模型账户、可用模型、API 接入与实际用量；未接通时页面明确提示未配置，不返回伪造的模型结果。
- 公开演示环境的浏览器执行能力与费用；在线网页不能凭一个 localhost 地址访问用户电脑，远程接入需要另行实现本地执行连接。
- 接入与维护验收的成本是否能被重复验收节省的工作抵消。
- 截图未明确的表单文件限制、应用 URL 的具体访问要求、开赛后指南中截图采集细则，以及赛前可复用内容的边界。已明确的提交要求见 `MING_SUBMISSION_CHECKLIST.md`。

范围取舍原则：优先让一个真实验收流程可靠完成，再增加适配范围。保留新项目和已有项目两类用途，不把它们扩展成两套庞大的功能。
