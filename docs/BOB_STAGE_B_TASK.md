## Implement within this stage

1. **Small server-side provider adapter.** Define a provider-independent request/result interface and one OpenAI-compatible HTTP transport for providers offering that protocol. Configure provider label, base URL, model ID and API key through ignored local server configuration/environment; provide a placeholder-only `.env.example`. No vendor-specific model assumption, provider marketplace or extra abstraction framework. Document how another protocol adapter can be added. Return only safe configuration status to the browser. Never send credentials into frontend bundles, model prompts, logs, stored requests or evidence. Use bounded timeouts and response sizes; report missing configuration, authentication, quota/rate limit, timeout, network and invalid-output errors distinctly. No silent fallback to the fixture and no endless retries.

2. **Saved project requirement and page context.** Add a minimal project/task record holding selected configured target, original requirement text and version. Keep execution on explicitly configured local test targets in Stage B; do not open unrestricted remote execution. Obtain bounded page structure (labels, roles, relevant visible elements/selectors) from that target for grounding. Do not upload project source, environment files or arbitrary local files. Treat page text as untrusted data; it helps locate controls but cannot redefine the user's expected behavior. If the target cannot be inspected, explain the blocker.

3. **Provider-generated drafts.** Supply original requirements, page context and the supported step schema to the adapter. Generate criteria with requirement-source references/quotes, expected behavior, prerequisites, questions/ambiguities and execution steps. Preserve the original text so references are inspectable. Unspecified business rules remain questions. Do not hardcode daily-report fields or silently substitute Stage A answers. Keep `source: fixture` for developer fixtures; reserve `source: generated` for actual provider-derived drafts, with a separate explicit live/test-transport provenance marker.

4. **Strict runtime validation.** Extend shared contracts minimally and validate model output before saving a usable draft or executing it. Reuse one validator at generation and run boundaries. TypeScript types alone are insufficient. Allow only registered actions/assertions and explicit fields, proper field types, bounded nonempty lists/strings, unique IDs, valid ordered dependencies/context inheritance, at least one actual assertion per executable criterion, and valid target/template references. Require count expectations to be nonnegative integers without coercion (`"2oops"` must fail). Reject unknown operations, scripts/eval and navigation outside the selected target policy. Resolve only documented variables such as `TARGET_URL` and `UNIQUE_CONTENT`; unresolved variables block execution. Invalid output returns readable errors and cannot create a passing report.

5. **Human confirmation and execution.** Add a simple web requirement form, generation state, readable draft review, source references and unresolved questions. Users should not need to read test code. Let them revise requirements/resolve questions and regenerate; a full visual plan editor is unnecessary. Confirmation must be an explicit action on the displayed plan ID/version/fingerprint and persist server-side. Unresolved material questions or invalid steps prevent confirmation. Running must never implicitly confirm a draft. Changed standards/plans require new confirmation; unchanged confirmed plans can rerun without another confirmation. Route selected confirmed plans through the existing runner, not a second execution engine. Preserve immutable snapshots and previous reports; bind runs to requirement, plan, target and test implementation versions/fingerprints.

6. **Honest usage and status.** Persist provider/model, invocation time, duration, success/error category and returned token usage when available, with a live/test marker. Missing token usage or cost is unknown, not zero. Do not invent prices. Show “model not configured” while keeping the clearly labeled Stage A fixture demonstration usable. Missing credentials must not appear as a working model integration.
